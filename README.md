# Lumen — стенд для интернал-ревью фронтенд-разработчика

Блог вымышленного продукта на **Next.js 16 (App Router)** с бэкендом на **Fastify + SQLite**.
Сайт работает, но в нём намеренно оставлены дефекты и незаконченные места — это и есть задания.

**Формат:** одна встреча на 90 минут, лайвкодинг с ревьюером, рассуждение вслух.
Шесть заданий идут по порядку, у каждого свой лимит времени. Два задания в резерве — на случай, если идём с опережением.

**Этот README читайте до сессии.** Код заданий до сессии не открываем — это договорённость.

---

## Правила

- **Гуглить можно.** Документация, MDN, Swagger, исходники в `node_modules` — тоже.
  Документация Next.js 16 лежит локально: `apps/web/node_modules/next/dist/docs/`.
- **AI-ассистенты нельзя** (Copilot, Cursor, ChatGPT, Claude и подобные).
- **Не успеть — нормально.** Лимит по заданию жёсткий: ревьюер остановит и переведёт дальше.
  Задания не зависят друг от друга, незакрытое не мешает следующему.
- **Говорите, что делаете.** Оценивается не только результат, но и как вы ищете причину, что проверяете
  и почему выбрали именно это решение.
- **Не согласны с формулировкой — скажите.** Аргументированное несогласие идёт в плюс.

**Не надо:** править `apps/api`, добавлять зависимости, переписывать ui-kit, менять тесты.

## До сессии

1. Поднять окружение и убедиться, что открываются http://localhost:3000/blog и http://localhost:3100/docs.
2. Проверить команды: `pnpm typecheck`, `pnpm lint`, `pnpm build` зелёные; `pnpm test` красный —
   падают **4 теста** в `@repo/core` (один `debounce` — T-02, три `throttle` — T-07).
3. Прочитать этот README целиком.

```bash
mise install               # node 24.21.0, pnpm 11.27.0
pnpm install
pnpm dev                   # оба приложения: сайт на :3000, API на :3100
```

База SQLite создаётся и наполняется 24 статьями при первом запуске API. Начать с чистого листа: `pnpm db:reset`.
Если что-то не поднимается — `docs/SETUP.md`.

## Как устроен проект

```
apps/web/src/
  app/blog/page.tsx               список статей: поиск, лента, пагинация
  app/blog/[slug]/page.tsx        страница статьи
  app/contact/                    форма: page.tsx, actions.ts (Server Action), form-state.ts
  app/admin/leads/page.tsx        служебная страница: что сохранила форма (кэш 60 с, тег leads)
  components/blog/                article-card, article-feed, search-box, use-infinite-list, reading-progress
  components/contact-form.tsx
  lib/api/                        client.ts (apiGet), schemas.ts, articles.ts, articles-client.ts, leads.ts
apps/api/                         Fastify + Drizzle + SQLite + Swagger — трогать не нужно
packages/core/src/timing/         debounce.ts, throttle.ts (+ тесты)
packages/contracts/src/           leadInputSchema, Result, safeFetch, toFieldErrorMap
packages/ui/                      ui-kit: atoms, FormField, Pagination, SiteHeader, SiteFooter, PageShell
```

Как ходят данные:

```
страница (Server Component)  →  lib/api/articles.ts  →  apiGet()  →  safeFetch()  →  zod-схема из lib/api/schemas.ts
клиентская лента             →  lib/api/articles-client.ts  →  та же схема, fetch из браузера
форма                        →  app/contact/actions.ts (Server Action)  →  POST /api/leads  →  /admin/leads
```

Что пригодится во всех заданиях:

- API отдаёт **snake_case**, даты — строками ISO 8601, списки — конвертом `{ items, total, page, per_page }`.
- Ответы API проходят через **zod-схемы** в `safeFetch`. Он ничего не бросает и возвращает `Result<T, FetchFailure>`.
  Тип данных — это `z.output` схемы: какая схема, такой и тип.
- Схема формы `leadInputSchema` из `@repo/contracts` **общая для фронта и бэка**.
- Кэш серверных запросов управляется через `revalidate` и `tags` в `apiGet`.

`pnpm tasks` печатает файлы и строки, где стоят маркеры заданий вида `[T-03]`.
У каждого задания ниже есть строка **«Начать с файла»** — это точка входа.

### T-04 · Форма на Server Action · 25 минут

**Симптомы.** Форма `/contact` отправляется, но проверьте четыре сценария: пустая форма; форма с одной ошибкой;
форма при выключенном API (`Ctrl+C` в терминале бэкенда); `/admin/leads` сразу после успешной отправки.

**Начать с файла.** `apps/web/src/app/contact/actions.ts`, рядом `form-state.ts`, потом `apps/web/src/components/contact-form.tsx`.

**Как это устроено.**

- У формы вместо `onSubmit` стоит `<form action={formAction}>`. Это **Server Action**: функция с `'use server'`
  в `actions.ts`, которая выполняется на сервере Next. Браузер отправляет `FormData` обычным POST,
  Next вызывает `submitContactForm(previousState, formData)`, а **возвращённый объект становится новым состоянием формы**.
  Поэтому action не бросает исключений и не редиректит: любой исход, включая ошибку, он описывает в `ContactFormState`.
- `useActionState(submitContactForm, initialContactState)` в `contact-form.tsx` возвращает три значения:
  текущее состояние, `formAction` для атрибута `action` и `isPending`, пока отправка идёт. Компонент читает из состояния
  ошибки полей, общую ошибку и введённые значения. Форма сейчас использует только первые два.
- **Без JavaScript форма тоже работает**: браузер делает POST, Next выполняет action и отдаёт перерисованную страницу.
  Отсюда правило: валидация и обработка ошибок живут в action, а не в `onSubmit` или `useState` на клиенте.
- После action **React сбрасывает неконтролируемую форму**. Чтобы ввод не пропал при ошибке, action возвращает
  введённое в `values`, а поля подставляют его через `defaultValue` (в разметке это уже сделано, не хватает данных).
- `leadInputSchema` из `@repo/contracts` — та же схема, которой валидирует бэкенд. Она принимает строки из `FormData`
  как есть: `consent` приводится из `'on'`, `budget` по умолчанию `'unknown'`. Результат `safeParse` при ошибке
  содержит `issues`, у каждого `path` (имя поля) и `message` (готовый текст для пользователя).
- Бэкенд отвечает `201` при успехе, `422` с массивом `errors: [{ path, message }]` при ошибке валидации
  и `429`, если с одного адреса больше 10 заявок в минуту. Скрытое поле `website` — honeypot: люди его не видят,
  боты заполняют, бэкенд на непустое отвечает `422`.
- `/admin/leads` читает список через `apiGet` с `revalidate: 60` и тегом `leads`: ответ лежит в **Data Cache** Next
  до минуты. Тот, кто записал заявку, обязан сбросить тег. В Server Action для этого есть `updateTag(tag)`:
  следующий запрос дождётся свежих данных. `revalidateTag(tag, 'max')` работает иначе: ещё раз отдаёт старое,
  а обновляет в фоне.

**Что сделать.**
1. В `form-state.ts` убрать `any` и сделать тип честным: `status` — объединение литералов `'idle' | 'success' | 'error'`;
   `fieldErrors` — сообщения по именам полей (`Partial<Record<Field, string[]>>`), где имена полей выводятся
   из `LeadInput`, а не перечисляются руками; `values` — введённые значения по тем же именам;
   `formError` — код ошибки (`'network' | 'rate-limited' | 'server'`), а не текст сервера, текст подберёт компонент.
   Зачем: компонент читает `fieldErrors.email[0]`, action кладёт массив, и компилятор сейчас об этом молчит.
2. В `actions.ts` валидировать `FormData` схемой `leadInputSchema` **до** запроса в API: ошибки разложить по полям
   и вернуть, в API не ходить. Зачем: пользователь видит ошибки без сетевого круга, сообщения совпадают с бэкендом.
   Ответ `422` разложить по полям так же (`toFieldErrorMap` уже есть в `@repo/contracts`).
3. Обработать сетевую ошибку (обернуть `fetch` в `try/catch`) и `429`: вернуть код в `formError`,
   чтобы пользователь увидел понятное сообщение, а не error boundary.
4. Во всех ошибочных ветках возвращать `values`, чтобы форма не теряла ввод. Значение honeypot возвращать не нужно.
5. После `201` сбросить кэш списка заявок по тегу `leads` (`LEADS_CACHE_TAG` из `lib/api/leads.ts`),
   чтобы `/admin/leads` показал заявку сразу. Выбрать `updateTag` или `revalidateTag` и объяснить, почему.
6. В `contact-form.tsx` взять третье значение `useActionState` и заблокировать кнопку на время отправки:
   иначе двойной клик даёт две заявки в базе. Текст общей ошибки подобрать по коду из `formError`.

**Готово, когда**
- [ ] пустая форма показывает ошибки под своими полями, введённое не теряется;
- [ ] `422` от API тоже раскладывается по полям;
- [ ] выключенный API и `429` дают понятное сообщение в форме;
- [ ] кнопка заблокирована, пока идёт отправка;
- [ ] `/admin/leads` показывает новую заявку сразу после успеха;
- [ ] в `form-state.ts` и `actions.ts` нет `any`; форма по-прежнему работает без JavaScript.

**Обсудим.** `updateTag` против `revalidateTag`. Зачем валидировать и на фронте, и на бэкенде.
Как описать состояние формы так, чтобы оно подошло другой форме (`FormState<TField>`). Как объявить результат скринридеру.

## Как проверять себя

- **Тесты:** `pnpm test:core` в watch-режиме.
- **Компилятор:** `pnpm typecheck`. После T-01 он становится главным помощником.
- **Браузер:** DevTools → Network (размер, формат, порядок загрузки), Console, Elements → Accessibility,
  режим устройства 360 px, «Просмотр кода страницы».
- **Заявки:** `/admin/leads` и `GET /api/leads` в Swagger.

Критерии «Готово, когда» — общие для вас и ревьюера.

## Заметки о стеке

- **Next.js 16:** Turbopack по умолчанию; `params` и `searchParams` — промисы; `revalidateTag` принимает второй
  аргумент, а в Server Actions есть `updateTag`; у `next/image` проп `priority` заменён на `preload`;
  `next lint` удалён, ESLint запускается напрямую.
- **React 19:** `useActionState` возвращает три значения; формы с `action` сбрасываются после отправки;
  атрибут `fetchpriority` в JSX пишется `fetchPriority`.

## Команды

```bash
pnpm dev             # оба приложения (turbo)
pnpm test            # все тесты один раз
pnpm test:core       # vitest в watch-режиме для @repo/core
pnpm typecheck       # tsc --noEmit по всему монорепозиторию
pnpm lint            # eslint
pnpm build           # прод-сборка (нужен запущенный API)
pnpm tasks           # где в коде лежит каждое задание
pnpm tasks T-03      # то же по одному заданию
pnpm db:reset        # пересоздать базу
```
